# MedPark 채권관리

덴탈 · 메디컬 · 에스테틱 세 사업부의 미수채권 잔액과 수금 진행을 관리하는 사내 웹 애플리케이션입니다.
Flask(Python 3.11) + React 단일 페이지 구조이며, 데이터는 **PostgreSQL**에 저장합니다.

---

## 1. 배포 전에 반드시 읽을 것

### 시연용 데이터가 들어 있습니다
원본 엑셀(미수채권현황)에서 추출한 실제 거래처 372건은 **이 패키지에 포함되어 있지 않습니다.**
최초 실행 시 `seed.py`가 9개 분류(3사업부 × 3채권분류)에 걸쳐 시연용 거래처 94건을 만듭니다.

실데이터는 이렇게 넣습니다.

1. `Medpark0` 또는 `Medpark3`으로 로그인
2. **출고 데이터 업로드** 화면 → 기준월 선택 → 엑셀 파일 업로드
3. 시연용 데이터가 있는 월(최초 실행한 달)을 같은 기준월로 덮어쓰면 시연 데이터는 사라집니다

### 초기 비밀번호
6개 계정 모두 초기 비밀번호는 `medpark2026!` 입니다.
**배포 직후 계정·권한 관리 화면에서 전부 변경하세요.**
환경변수 `DEFAULT_PASSWORD`를 설정하면 최초 생성 시 그 값이 쓰입니다.

| 아이디 | 이름 | 역할 | 사업부 |
|---|---|---|---|
| Medpark0 | 시스템관리자 | 시스템관리자 (권한 11종 전부) | – |
| Medpark1 | 대표이사 | 임원 | – |
| Medpark2 | 김태현 상무 | 임원 | – |
| Medpark3 | 김홍윤 수석 | 재무담당 (수금 승인·업로드·마감) | – |
| Medpark4 | 박재흥 | 영업담당 | 덴탈 |

## 2. AI Space 배포

- 런타임: **python** (3.11)
- 데이터베이스: **없어도 됩니다.** DB 서버 없이 배포하면 SQLite 파일로 동작하고,
  나중에 PostgreSQL을 붙이면 코드 수정 없이 그쪽으로 전환됩니다
- 배포 공간: space_05

실행 명령은 `Procfile`에 정의되어 있습니다.

```
web: gunicorn -w 2 -k gthread --threads 4 -b 0.0.0.0:${PORT:-8000} --timeout 120 app:app
```

### 데이터베이스 연결
접속정보는 AI Space가 주입하는 환경변수를 그대로 씁니다.
**직접 설정할 필요가 없고, 코드에 하드코딩된 값도 없습니다.**

```
DB_HOST  DB_PORT  DB_NAME  DB_USER  DB_PASSWORD
```

`DB_BACKEND` 로 동작을 고정할 수 있습니다.

| 값 | 동작 |
|---|---|
| `auto` (기본) | `DB_HOST`가 있으면 PostgreSQL, 없으면 SQLite |
| `sqlite` | DB 접속정보가 주입돼도 무시하고 파일 DB 사용 |
| `postgres` | 반드시 PostgreSQL로 붙고, 안 되면 기동 실패 |

플랫폼이 MySQL 등 다른 종류의 접속정보를 주입해 버리면 PostgreSQL 드라이버가 접속에
실패해 컨테이너가 뜨지 않습니다. **그때는 `DB_BACKEND=sqlite` 를 넣으면 즉시 복구됩니다.**

현재 접속 대상은 `/health` 에서 확인합니다.

```json
{"status":"ok","db":"SQLite (/app/user_data/ar.db)","journal":"wal","time":"..."}
{"status":"ok","db":"PostgreSQL (psycopg2)","journal":null,"time":"..."}
```

`journal` 이 `wal` 이 아니면 저장 볼륨이 WAL을 지원하지 않는다는 뜻입니다. 동작에는 문제가
없고 동시 쓰기가 조금 더 직렬화될 뿐입니다.

### DB 서버 없이 운영할 때
아래는 워커 2개 · 스레드 8개로 실제 측정한 값입니다.

| 항목 | 결과 |
|---|---|
| 메모리 | 워커 2개 합계 약 75MB (space_05 한도 256MB) |
| 디스크 | 거래처 494건 기준 250KB (한도 1GB) |
| 동시 등록 | 120건 / 1.7초 / 충돌 0 |
| 동시 승인 | 120건 / 1.2초 / 잔액 정합성 일치 |
| 400행 업로드 | 0.01초 |
| 전체 조회 | 0.01초 / 응답 221KB |

이 규모에서는 SQLite로 충분합니다. PostgreSQL이 필요해지는 시점은 여러 서비스가 같은
데이터를 공유해야 할 때이지, 지금의 데이터량이나 사용자 수 때문이 아닙니다.

### 나중에 PostgreSQL로 옮기기
`migrate_to_postgres.py` 가 SQLite 데이터를 PostgreSQL로 옮깁니다.

```bash
export DB_HOST=... DB_PORT=5432 DB_NAME=ar DB_USER=ar DB_PASSWORD=...
python migrate_to_postgres.py            # 미리보기 — 무엇이 몇 건 옮겨지는지만 출력
python migrate_to_postgres.py --apply     # 실제 이관
```

8개 테이블을 모두 옮기고, 자동 증가 키의 시퀀스를 최대값 뒤로 재설정합니다.
이관 후 앱을 재기동하고 `/health` 의 `db` 값이 PostgreSQL인지 확인하세요.
원본 SQLite 파일은 지우지 말고 보관하는 편이 안전합니다.

테이블은 최초 기동 시 자동 생성됩니다. gunicorn 워커가 둘이므로 초기화가 겹치지 않도록
PostgreSQL 자문 잠금(`pg_advisory_xact_lock`)을 걸어 두었습니다.
컨테이너가 DB보다 먼저 뜨는 경우를 대비해 최대 30초까지 접속을 재시도합니다.

### 영속성
| 대상 | 위치 | 재배포 시 |
|---|---|---|
| 거래처·수금·목표·계정 | PostgreSQL 또는 `/app/user_data/ar.db` | 유지 |
| 세션 서명 키 | `/app/user_data/secret_key` | 유지 |

`/app/user_data/` 는 AI Space에서 재배포 후에도 보존되는 유일한 경로입니다.
**절대 다른 위치로 바꾸지 마세요.**

`update_project`로 코드만 갱신하면 데이터는 그대로입니다.
프로젝트 삭제는 DB까지 지웁니다. 사전에 `backup_project`를 받으세요 (DB 덤프가 자동 포함됩니다).

### 시각 처리
서버 시간대가 UTC여도 화면에는 한국 시각이 나오도록,
등록·승인·업로드 시각은 `now() AT TIME ZONE 'Asia/Seoul'` 로 저장합니다.

### 환경변수 (선택)
| 이름 | 기본값 | 설명 |
|---|---|---|
| `SECRET_KEY` | 자동 생성 | 세션 서명 키. 지정하면 재배포 후에도 로그인 세션이 유지됩니다 |
| `DEFAULT_PASSWORD` | `medpark2026!` | 계정 최초 생성 시 비밀번호 |
| `PORT` | 8000 | 수신 포트 |

### 외부 의존성
브라우저가 다음 세 가지를 CDN(`cdn.jsdelivr.net`)에서 내려받습니다.

- React 18 / ReactDOM 18 — 화면 렌더링
- SheetJS 0.18 — 엑셀 파싱
- Pretendard — 한글 글꼴 (실패해도 시스템 글꼴로 대체됨)

사내망에서 이 도메인이 막혀 있으면 로그인 화면 대신 안내 문구가 뜹니다.
그 경우 해당 파일들을 `static/`에 내려받아 두고 `templates/index.html`의 script 경로만 바꾸면 됩니다.

## 3. 화면과 권한

권한은 11종이며 계정마다 개별 지정합니다. 역할 템플릿(시스템관리자 / 임원 / 재무담당 / 영업담당)을
누르면 해당 조합이 한 번에 채워지고, 이후 체크박스로 조정할 수 있습니다.
권한이 없는 화면은 좌측 메뉴에 아예 나타나지 않습니다.

| 화면 | 필요 권한 | 하는 일 |
|---|---|---|
| 대시보드 | `dashboard_view` | KPI 4종, 사업부별 채권 분류, 월별 수금 실적, TOP5, 수금목표 요약, 담당자별 현황 |
| 거래처별 현황 | `customer_view` | 사업부 → 채권분류 2단계 트리, 검색, 비고 인라인 편집 |
| 담당자별 채권현황 | `owner_view` | 담당자별 잔액 구성과 담당 거래처 목록 |
| 수금 등록 | `collection_register` / `collection_approve` | 영업담당 입력 → 재무담당 승인 후 잔액 반영 |
| 수금목표 관리 | `target_manage` | 목표일·완료일·수금방법·담당자·비고 |
| 출고 데이터 업로드 | `upload_data` | 엑셀 업로드, 월 단위 교체, 업로드 이력 |
| 계정·권한 관리 | `user_manage` | 계정 생성·정지, 비밀번호 재설정, 권한 편집 |

나머지 권한: `note_edit`(비고 편집), `month_lock`(마감 잠금·해제), `data_export`(내보내기).

### 수금 처리 흐름
등록된 수금 건은 `승인 대기` 상태로 들어가며, **승인 시점에만** 거래처 잔액이 줄어듭니다.
잔액이 0이 되면 채권분류가 자동으로 `정상`으로 바뀝니다. 반려하면 잔액은 그대로입니다.
같은 건을 두 번 승인할 수 없습니다.

## 4. 엑셀 업로드 규칙

첫 번째 시트를 읽습니다. 앞쪽 15행 안에서 `거래처코드`와 `거래처명`이 함께 있는 행을 머리글로 잡으므로,
제목 행이나 빈 행이 위에 있어도 됩니다.

인식하는 열 (괄호 안은 같이 인식되는 이름):

| 항목 | 열 이름 |
|---|---|
| 거래처코드 | 거래처코드 (코드, 고객코드) |
| 거래처명 | 거래처명 (거래처, 업체명, 고객명) |
| 사업부 | 사업부 (사업부문, 부문) |
| 채권분류 | 채권분류 (분류, 채권상태, 상태) |
| 담당자 | 담당자 (영업담당, 담당) |
| 미수잔액 | 미수잔액 (미수금액, 채권잔액, 잔액, 미수금) |
| 선수금 | 선수금 (선수금액) |
| 경과일 | 경과일 (연체일, 경과일수, 연체일수) |
| 최종수금일 | 최종수금일 (최근수금일, 최종입금일) |
| 비고 | 비고 (특이사항, 메모) |

자동 처리되는 것들:

- 채권분류 열이 비어 있으면 경과일로 판정합니다 — 30일 이하 `정상`, 180일 이하 `연체`, 그 이상 `부실`
- 거래처코드가 비었거나 `#REF!`, `#N/A` 인 행은 건너뜁니다 (원본 엑셀의 VLOOKUP 오류 대응)
- 같은 코드가 두 번 나오면 마지막 값으로 덮어씁니다 (중복 행 대응). 업로드 전 미리보기에 건수가 표시됩니다
- 금액의 쉼표는 제거하고 숫자로 읽습니다

### 월 단위 교체
업로드는 **선택한 기준월의 데이터만** 교체합니다. 다른 월 데이터는 건드리지 않습니다.
같은 달을 다시 올리면 그 달 것만 새 파일로 바뀝니다.

### 마감 잠금
잠금은 **수동입니다.** 날짜가 지났다고 자동으로 잠기지 않습니다.
`month_lock` 권한이 있는 사람이 직접 잠그고 직접 해제합니다. 잠긴 달은 업로드가 거부됩니다.

## 5. 로컬에서 실행

```bash
pip install -r requirements.txt
python app.py          # http://127.0.0.1:8000
```

`DB_HOST` 가 없으면 SQLite 파일(`user_data/ar.db` 또는 `/app/user_data/ar.db`)로 동작하므로
PostgreSQL 없이도 그대로 띄워볼 수 있습니다. 로컬에서 PostgreSQL에 붙이려면:

```bash
export DB_HOST=localhost DB_PORT=5432 DB_NAME=ar DB_USER=ar DB_PASSWORD=...
python app.py
```

SQL은 PostgreSQL 문법 한 벌만 관리합니다(`%s` 자리표시자, `ON CONFLICT`, `RETURNING`).
SQLite로 실행할 때는 `db.py` 가 자리표시자만 `?` 로 바꿔 같은 쿼리를 돌립니다.

## 6. 화면 코드를 수정할 때

브라우저에서 실행되는 파일은 `static/app.js` 이고, 사람이 읽고 고치는 원본은 `static/app.jsx` 입니다.
JSX를 고친 뒤에는 반드시 다시 컴파일해야 화면에 반영됩니다.

```bash
npx tsc static/app.jsx --jsx react --target es2018 --outDir /tmp/out --skipLibCheck
cp /tmp/out/app.js static/app.js
```

타입 관련 경고(TS7006, TS18046 등)는 무시해도 됩니다. 그래도 파일은 정상적으로 생성됩니다.

> 브라우저에서 JSX를 실시간 변환하지 않는 이유: Babel standalone은 약 3MB이고 화면을 열 때마다
> 1,300줄을 다시 변환합니다. 미리 컴파일해 두면 첫 화면이 눈에 띄게 빨라집니다.

### 반제품 출고 업로드

- 아마란스10 대분류 `반제품_덴탈_국내`, `반제품_메디컬_국내`, `반제품_에스테틱_국내`도 해당 사업부의 채권으로 반영합니다.
- 대분류에 `반제품`만 있으면 미리보기 표에서 각 행의 사업부를 선택해야 반영할 수 있습니다. 선택 전에는 같은 거래처의 반제품 행도 합치지 않습니다.
- 제품·반제품의 합계액(AB열)을 기존 고객코드·사업부·출고월 기준으로 합산하며, 마감월 제외와 기존 사업부 수정 이력 적용은 유지합니다.

회귀 검증은 `requirements.txt` 설치 후 `python -m unittest discover -s tests -p 'test_*.py' -v`로 실행합니다. API 검증은 임시 SQLite DB만 사용합니다.
화면 검증은 `xlsx@0.18.5`가 설치된 환경에서 `node --test tests/upload.test.cjs`로 실행합니다. 실제 XLSX 파일을 만들어 컴파일된 화면의 파싱·사업부 선택·업로드 요청을 검증합니다.

## 7. 파일 구성

### 수금등록 데이터 업로드 (2026-09-08)

수금 메뉴에서 수금 등록과 같은 단계에 표시됩니다. `collection_register` 또는
`collection_approve` 권한으로 파일을 검증하고 일괄등록합니다. 업로드 화면에서 승인권자는 최종 등록과 동시에 자동 승인·상계하며, 승인 권한이 없는 등록자는 승인 대기로 등록합니다. 서버의 승인 권한 검사는 유지합니다.

- 첫 시트의 앞 25행에서 머리글을 탐색합니다. 고객코드를 정확히 매칭하며 관리번호·관리고객코드는 사용하지 않습니다.
- 필수 열: 고객코드, 수금일자, 수금번호, 순번, 수금구분, 수금구분유형, 정상수금, 선수금.
- 제예금(유형 1) → 계좌수금, 카드(유형 5) → 카드수금. 공백을 제거합니다. 어음은 확인된 어음 명칭으로 판정하며 미확인 숫자 유형코드를 임의로 추정하지 않습니다.
- 수금액은 정상수금+선수금이며 원 단위 0 이상 정수, 합계는 양수여야 합니다. 합계행은 제외하고 실제 내역과 합계를 대조합니다.
- 수금번호+순번을 DB 고유키로 보존합니다. 동일 내역 재전송, 내용이 달라진 동일 키, 파일 내 중복 키는 오류 대신 확인 팝업에서 비교하고 등록자가 확인 체크하여 제외합니다. 번호·순번이 같은 행을 별도 생성하거나 기존 값을 덮어쓰지 않습니다.
- 중복 처리는 최종 등록과 분리됩니다. 입력 오류가 있어도 본문 상·하단의 중복 처리 버튼, 행별 버튼 또는 거래처 팝업의 중복 먼저 처리로 열 수 있습니다. 팝업의 중복 확인 적용은 현재 화면의 선택만 반영하며 DB를 변경하지 않습니다. 본문의 등록 진행 버튼은 남은 거래처 선택·재검증, 중복 확인 또는 입력 오류 보기로 연결됩니다. 실제 등록 요청은 오류가 없고 최신 거래처 선택 및 모든 중복 판단이 적용된 경우에만 전송합니다.
- 거래처 재검증 시 행의 비교 토큰이 같으면 중복 선택과 적용 상태를 유지하고, 토큰이 바뀐 후보는 확인을 초기화합니다. 거래처 또는 중복 선택을 수정하면 다시 적용해야 합니다. 적용 전 거래처 선택으로 예전 확인 결과를 등록하지 않습니다. 새 파일 선택·새로고침 시 확인을 다시 진행합니다. 서버는 최종 등록 시 최신 상태와 모든 확인 결과를 계속 검증합니다.
- 고객·날짜·금액·방법이 기존 수금과 같지만 번호·순번이 다른 후보는 중복 제외 또는 사유(5~500자)를 입력한 별도 수금 등록을 선택하고 확인 체크합니다. 확인 없는 요청은 409와 최신 미리보기를 반환합니다.
- 확인 토큰은 각 업로드 행과 기존 후보의 최신 상태에 연결됩니다. 확인 뒤 원본·기존 수금이 달라지거나 다른 사용자가 먼저 등록하면 재확인해야 합니다. 신규 건은 중복 확인 완료 후 계속 등록합니다.
- 입력 오류는 행·거래처명·고객코드·수금번호·사유로 본문과 팝업에 표시하고 오류만 보기 필터를 제공합니다. 날짜·금액 오류, 수금구분 충돌, 수금년월 불일치, 마감월, 원장잔액 불일치는 수정 전 전체 등록을 중단합니다.
- 미등록/모호한 코드는 거래처 확인 창에서 기존 거래처 연결, 신규 등록, 이번 업로드 제외를 명시적으로 선택합니다. 같은 이름은 공백 제거 기준으로 후보만 표시하고 자동 연결하지 않습니다. 같은 원본 코드는 파일 내 모든 행에 같은 결정을 적용합니다.
- 기존 연결은 표시된 후보의 코드·사업부·잔액을 비교하고 5~500자 사유 및 확인 체크가 필요합니다. 원본 코드와 기존 코드는 보존하며 매핑은 이번 업로드에만 적용합니다. 연결 후 대상 고객 기준으로 중복 수금을 재검사합니다.
- 신규 거래처 등록은 `collection_register` 권한, 이름, 사업부, 확인 체크가 필요합니다. 잔액 0원·회수기간 미입력으로 시작하며 수금 승인 시 선수금으로 처리합니다. 같은 이름이라도 신규 등록을 선택하면 기존 채권과 분리됩니다.
- 거래처 선택 및 재검증은 읽기 전용입니다. 최종 등록 트랜잭션 안에서 실제 신규 수금에 필요한 거래처만 생성하며 실패하면 거래처와 수금 모두 롤백합니다. 거래처 확인 후 제외한 행도 이력을 남기며 다른 행은 계속 진행합니다.
- 거래처 선택 토큰은 파일과 최신 후보의 코드·이름·사업부·집계/원장잔액·허용 동작에 연결됩니다. 동시 신규 등록이나 후보 변경 시 재확인을 요구하고 미확인·잘못된 대상·권한 없는 신규 등록을 거절합니다.
- 승인 시 기존 부실→미수→정상 순서를 공유하며 오래된 발생월부터 상계합니다. 실제 미상계액만 선수금으로 보존하고 최종수금일이 과거로 돌아가지 않도록 합니다.
- 업로드 이력·수금번호/순번·원본 핵심값은 `collection_upload_batches`, `collection_import_rows`에 보존합니다. 중복 및 거래처 판단·확인자·시각·비교값은 `collection_upload_reviews`에 기록하며 화면에서 확인 이력을 조회합니다. 거래처 확인은 `customer_link`, `customer_create`, `customer_exclude`로 구분합니다. 전부 제외한 파일도 확인 이력을 남깁니다. 기존 행 삭제/초기화는 없습니다.
- 등록/승인/출고 교체/마감 처리는 PostgreSQL 트랜잭션 자문 잠금으로 직렬화합니다. 로컬 SQLite 검증에서는 즉시 쓰기 트랜잭션을 사용합니다.
- 화면의 사용 매뉴얼에 입력 기준·오류 조건·상계 기준·권한을 추가했습니다.

### 채권·수금 추이 / 상세내역 (2026-09-08)

`채권요약현황` 바로 아래 `채권·수금 추이`, `채권·수금 상세내역`을 표시합니다.
두 화면과 모든 조회 API는 `dashboard_view` 권한이 필요합니다. 기존 요약 스냅샷 선택과 구분하여 현재 운영 원장으로 조회합니다.

- 추이는 기본 최근 6개월 월별 조회입니다. 시작월·종료월(최대 24개월), 사업부, 거래처명·고객코드 필터, 일별·월별 전환을 지원합니다. 그래프·기간별 금액표·금액 카드를 누르면 같은 조건의 세부 내역으로 이동합니다.
- 출고 발생액은 현재 `monthly_shipment_units.amount`에 반영된 월별 원금입니다. 상계 후 `balance`를 발생액으로 사용하지 않으며 반품·취소·조정의 음수를 보존합니다. 같은 월의 과거 업로드를 더하지 않습니다.
- 승인 수금은 `collections.state='approved'`의 전체 수금액을 `paid_at`으로 집계합니다. 선수금을 포함하며 승인 대기·반려·중복 확인 제외 행은 승인 실적에서 제외합니다. 사업부는 현재 거래처 마스터의 사업부 기준이며 실제 채권별 상계 배분을 의미하지 않습니다.
- 발생액−수금액은 기간 내 흐름 비교입니다. 기초 잔액·선수금·조정 등의 차이 때문에 현재 채권잔액과 같지 않습니다. 기초·이월 원장은 발생액 그래프에서 제외하고 별도 탭에 현재 원금·잔액을 표시하며 해당 탭에는 기간 필터를 적용하지 않습니다.
- 출고 원본은 새 `shipment_upload_lines` 테이블에 업로드 ID, 엑셀 행 번호, 출고일, 고객코드, 원본 사업부, signed 금액, 원본 셀 값을 저장합니다. 클라이언트가 월·고객·사업부로 합산하더라도 `source_lines`를 함께 보내 원본 날짜를 보존합니다. 서버는 원본 합계 일치·날짜·정수 금액을 저장 전 확인하고 출고 반영과 같은 트랜잭션으로 저장합니다. 최대 50,000개 상세 행, 기존 요청 크기 24MB 제한을 적용합니다.
- 해당 월의 최신 출고 업로드 ID에 속한 원본 행만 현재 월별 원금과 대조해 사용합니다. 사업부 수정 이력을 적용합니다. 원본 미보관 또는 상세 합계 불일치 시 월별 원금을 사용하고 날짜 미보관으로 표시합니다. 과거 업로드 날짜나 월말을 실제 출고일로 추정하지 않습니다. 일별 그래프는 날짜를 확인한 금액만 표시하고 제외된 월별 금액과 내역 수를 안내합니다. 월별 그래프는 미보관 금액까지 포함합니다.
- 과거 일자별 원본을 확보하려면 해당 월의 전체 출고 엑셀을 기존 재업로드 방식으로 반영합니다. 일부 행만 다시 올리면 월 전체가 교체되므로 전체 월 자료가 필요합니다. 업로드 복원은 해당 버전의 상세 행을 삭제하고 이전 최신 버전으로 돌아갑니다. 기존 수금 이후 복원 방지 규칙을 유지합니다.
- 상세내역은 서버에서 50개씩 페이지를 나눕니다. 출고·수금별 특정 일자/월, 수금 상태·수기/업로드 경로로 조회할 수 있습니다. 합계는 현재 페이지가 아닌 조건에 맞는 전체 내역의 합계입니다. 업로드 원본 팝업은 파일명·등록자·등록시각·원본 필드를 표시합니다. 제외 판단의 감사 이력은 기존 수금 업로드 이력에서 확인합니다.
- API: `GET /api/receivable-activity`, `GET /api/receivable-activity/details`, `GET /api/receivable-activity/source/{shipments|collections}/{id}`. 보고서의 다중 조회는 동일 DB 스냅샷에서 실행합니다. 보고서 조회로 수금·채권을 변경하지 않습니다.
- 빌드: 기존 `app.jsx`와 함께 `static/activity.jsx`를 React JSX/ES2018로 컴파일하여 각각 `static/app.js`, `static/activity.js`에 반영합니다. HTML에서 `activity.js`를 `app.js`보다 먼저 로드합니다. JS·CSS 내용 해시로 정적 자산 캐시 버전을 갱신합니다.
